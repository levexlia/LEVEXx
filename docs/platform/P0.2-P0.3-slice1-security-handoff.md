Trigger invocation is automatic for DML admitted by grants and RLS. It does not supply DML authority or replace application authorization. Direct trigger-function invocation, routine EXECUTE grants and trigger creation/disable rights must be verified on the supported PostgreSQL version rather than assumed.

Both functions: fixed `search_path = pg_catalog, levex_private`; schema-qualified objects; no dynamic SQL; no TG_ARGV parameters; no caller/requester parameters; no generic query input; no privileged helper call; no sensitive diagnostic payload. Functions must be attached only to their inventoried table/operation and return NEW only after validation. Owners and attachments are checked in CI.

### Account guard

Reject any change to id, actor_id, provider, provider_subject or created_at using NULL-safe OLD/NEW comparisons. Lifecycle fields retain canonical v1 checks and version semantics; this guard does not add a public account update capability.

### Role guard

On UPDATE reject changes to id, actor_id, role, assignment_source, assigned_by_actor_id, assigned_at or created_at. Reject reactivation or reuse of a REVOKED row. Permit only the canonical ACTIVE → REVOKED transition with valid revoke metadata and version/timestamp update. Do not create a new role-administration endpoint in this slice.

On runtime INSERT require OPERATOR source and assigned_by_actor_id equal to the non-null validated current actor. On runtime revoke require revoked_by_actor_id equal to that actor. Existing RLS and application rules must still establish current operator authority and prohibit operator self-mutation; a GUC alone cannot grant authority.

BOOTSTRAP handling requires explicit review: permit only the canonical migration/provisioning authority, never runtime and never a caller-supplied flag. Preserve the existing BOOTSTRAP assigned_by NULL constraint. Do not add owner write policies merely to make seeding convenient. The implementation must document and test how provisioning inserts coexist with FORCE RLS before exposing any write path.

### Migration ordering

The first slice creates security, identity and authorization migrations only. Context helpers and general runtime grants appear later in the canonical migration plan. The amendment must specify dependency ordering for attribution checks before runtime role writes can be granted. First-slice tables must remain fail-closed without premature runtime write authority; do not silently advance to cohort/context/RLS slices to make the proposal executable.
