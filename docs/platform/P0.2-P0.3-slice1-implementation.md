## Implemented scope

- Dedicated-database provisioning: exactly four canonical roles, NOINHERIT, NOSUPERUSER, NOBYPASSRLS, NOCREATEDB, NOCREATEROLE, NOREPLICATION. `db_owner` is NOLOGIN; only `migrator` can SET ROLE to it. Existing unsafe role configurations cause failure instead of silent repair.
- Three new migrations: `1790000000001_p02-db-security.cjs`, `1790000000002_p02-identity.cjs`, `1790000000003_p02-authorization.cjs`. Gate 0 migration is unchanged.
- `levex.actors`, `levex.accounts`, `levex.role_assignments`: v1 fields, CHECK/FK constraints, provider-subject uniqueness, partial unique ACTIVE role per actor, indexes and history guards.
- Both approved `levex_private` trigger functions are SECURITY INVOKER, owned by `db_owner`, with exact `pg_catalog, levex_private, pg_temp` search path. No PUBLIC/runtime EXECUTE, helper calls, table queries, dynamic SQL or sensitive errors.
- Phase A role guard accepts only canonical migrator-session/owner-effective-role ACTIVE BOOTSTRAP INSERTs. All role UPDATEs and OPERATOR INSERTs remain denied until Phase B.
- ENABLE + FORCE RLS on all three tables; zero policies and zero runtime domain/column grants. No account/role runtime mutation is exposed. No identity resolver, actor-context helper, cohort, guardian, consent or Phase B implementation is included.
- Identity binding validation is input validation only; it neither authenticates a provider nor resolves an actor.

## Provisioning and test boundary

Production credentials are never generated, stored or read by this work. `db:provision` requires explicit provisioning connection and role-password environment variables for a dedicated database. `db:migrate` requires a real `migrator` login and PostgreSQL 18.6; it refuses a superuser or impersonated session.

A1 allows migration/provisioning authority but supplies no runtime or owner write policy. Accordingly the shipped schema denies even db_owner DML under FORCE RLS. The tests use an explicitly isolated migration-authority transaction with RLS temporarily disabled, and always roll it back, to prove bootstrap and guards. This is not a standing provisioning endpoint or a runtime privilege path. A future reviewed data migration must establish its own transactional seeding boundary and restore ENABLE/FORCE before commit.

The revoked-history test imports a historical fixture with the trigger temporarily disabled by the migration owner, reenables it before exercising the rejection, and rolls back the fixture. It does not claim Phase A supports creating/revoking runtime history.

TRIGGER-008 tests the PostgreSQL invocation mechanism using temporary test-only grants/policies within a transaction and the app effective role. All are rolled back, and phase-A containment is rechecked. It does not validate the later actor-context service or Phase B role trigger.
